# shortlist-crosscheck — 设计（简版）

日期：2026-11-14 · 来源：research-spark 中 York Region 午餐调研（`life/York-Region-Lunch/`）

## 意图与原因
用户手上已有一份候选名单（来自任一 digest 或自己列的），要在做决定前，跨平台逐项核实，避免被单一来源误导。这次实测：小红书推荐的 13 家餐厅里，1 家暂停营业、1 家不做午餐、1 家地址写错、1 家店名不对、3 家英文评分明显偏低、1 家好评来自赞助文、1 家评价数量涨得异常快。体检还揪出 1 处把别家的评价算到这家头上。

## 目标
- 适用多个领域：餐厅/本地商家、产品、旅行地点、课程、活动，以后还能加。
- 对每个候选核实：**身份**（名字/型号/地址）→ **现在能不能用**（营业、有货、能报名、日期没过）→ **多平台信号**（评分、评价数、近期评价）→ **危险信号**（赞助/联盟推广、评价涨得异常快、刚开业或主办方太新、平台之间评分差很大）。
- 输出每项的 ✅ / ⚠️ / ❌ 初筛和证据，**结论留给用户**。

## 不做的事
- 不找候选（那是 digest 或用户的事）。
- 不根据用户的个人情况（时间、预算、人数）下最终推荐。
- 不替代 digest：只抽取核实需要的信号，不做主题综述。

## 反目标（做了也算失败）
- 把搜索摘要当成读过原帖，或把单一来源写成共识。
- 证据归属错误（A 的评价算到 B 头上）。
- 用 curl/WebFetch 去访问容易被 block 的站点。

## 方案（已选 A）
- **A. 独立的核实 skill（已选）**：和三个 digest 都不耦合，任何来源的名单都能用。
- B. 在每个 digest 里加核实模式：同一套逻辑要写三遍，跨平台的核实也不该挂在某一个来源下面。
- C. 一个包揽搜索、digest、核实、合并的大 skill：违背"各来源互不依赖、需要时才合并"的原则。

## 已定的做法
- 放在 my-skills-marketplace，作为 `plugins/shortlist-crosscheck/`，按 `add-skill.sh` 走审核流程。
- 所有页面访问都走 browser-use；小红书走 xhs MCP。
- 流程：
  1. 确认名单和类别
  2. 对每个候选做一次 Google 搜索（信息面板 + 第三方评分摘要），需要时补查对应平台
  3. 用 `site:` 搜索找社区讨论，挑重点帖子读全文和评论
  4. 存原始文件到 `raw/`
  5. 写对照表
  6. 体检：用脚本核对每条引文能在 `raw/` 里找到；人工逐条核对 md 的每个说法，尤其是"说的是不是这一家"
- 输出写到话题目录：`crosscheck-YYYY-MM.json`（证据）和 `crosscheck-YYYY-MM.md`（中文对照表 + 规律 + 待确认）。
- 各类别去哪些平台查，先作为 SKILL.md 里的一张表；某个类别的规则变多了，再拆成 `references/<类别>.md`。

## 留给实现者
- 类别表每个格子具体写哪些平台。
- 每项判 ✅ / ⚠️ / ❌ 的具体标准怎么写。
- 用一次真实任务验证（建议用非餐厅类别，例如一款产品），跑完再加一个证据审计 agent 复查。
